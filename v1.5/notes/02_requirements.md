## 2 | 2장 요구사항 정의 — 무엇을 해야 하는가
> 2장은 서비스 흐름, 데이터·AI 요구, 유스케이스, 기능 요구(운영자·관리자·시스템), 비기능 요구 순서로 "무엇을"을 정의합니다. 모든 요구에 ID 를 붙여 화면·시퀀스·API·시험까지 추적합니다.

ID 규칙만 알면 문서 전체를 따라갈 수 있다: FR-U(운영자 기능), FR-A(관리자), FR-S(시스템 자동), AI-0N(AI), FR-E(실험), NFR(비기능), SC(화면), SD(시퀀스), API, FN(함수). 연결표는 부록 A.1.

## 2.1 | 서비스 구성 및 개요
> 서비스는 데이터 수집 → AI 학습 → AI 서비스 → 웹 화면 네 부분이고, 운영 루프와 학습 루프 두 순환이 FMS 의 ai_adapter 에서 만납니다.

## 그림 2.1 | 서비스 시나리오 구성도
> ①~③은 실시간으로 도는 운영 루프, ④~⑧은 운행 기록으로 모델을 만들고 되돌리는 학습 루프입니다.

그림을 가리키며 번호 순서로 한 바퀴 돈다. 핵심 메시지는 "학습 루프는 오프라인, 운영 루프는 실시간"이라 AI 학습이 늦어도 관제는 멈추지 않는다는 점이다.

## 표 2.1 | 서비스 절차와 효과
> 절차마다 "그래서 무엇이 좋아지나"를 오른쪽 열에 적었습니다.

짚을 곳:
- ②: 예약을 MQTT 로 보내기 **전에** `traffic.json` 에 저장한다. FMS 가 발행 직후 죽어도 재시작하면 예약이 남아 있어 같은 존에 두 대를 허가하지 않는다.
- ③: 허가·해제는 시간이 아니라 위치 증거로 한다. 통신이 늦어도 겹치지 않는 이유다.
- ⑤: 특징은 "배정 순간에 알던 값"으로만 만든다. 미래 정보가 섞이면 평가가 부풀려진다.
- ⑥: 결과 보고 형식이 "규칙 대비 N% 개선"이다.

Q: 외부 시스템이 같은 주문을 두 번 보내면?
A: `external_id` 멱등 키로 같은 작업을 한 번만 만듭니다(API-401).

## 주요 서비스 시나리오 | 주요 서비스 시나리오
> 제안서 24쪽 시나리오 S1~S12 를 같은 ID 로 받아 각각 상태와 시퀀스 번호를 붙였습니다.

## 표 2.2 | 서비스 시나리오 S1~S12
> 12개 중 8개는 이미 동작하고, S4 교착 해소·S5 장애 재배정은 일부, S8 예측 통로 선택·S9 이상 점검·S12 성능 실험이 이번 개발입니다.

- **S5 문구 차이**: 제안서는 "점유 해제 후 재배정"이라고 썼지만 설계서는 "작업은 재배정, 점유는 위치 증거가 있을 때만 해제"로 정했다. 통신이 끊긴 로봇이 실제로는 존 안에 서 있을 수 있기 때문이다(6.2 SD-05 상자, 부록 A.2).
- 9장 시험에서 S1~S12 를 체크리스트로 그대로 확인한다.

Q: S3 "통로 마주침"은 실제로 확인했나?
A: 물리 통합 시험(`physics_test.py traffic`)과 시뮬레이터 head_on 시나리오에 이 장면이 들어 있고, 12/09·12/10 시험 계획(표 9.8)에서 다시 돌려 결과를 남깁니다.

! 발표 전에 이 시험을 한 번 돌려 보고 "확인했다"고 말할지 정한다. 돌려 보지 않았으면 "시험 시나리오가 있다"까지만 말한다.

## 2.2 | 데이터분석의 요구사항
> 학습 데이터는 모두 시뮬레이터 운행에서 얻으므로, 결과 해석도 "시뮬레이션 기준"으로 한정합니다.

## 표 2.3 | 데이터분석 요구사항 DR-01~09
> 로봇 State, 교통 대기, 배정, 작업 이력, 이상 주입, 운행 메타 여섯 종의 원본과 다양성·분량·품질 기준을 정했습니다.

- DR-02 의 굵은 글씨(zone_id·gate_id·대기열 길이)가 이번 개발에서 이벤트에 추가할 필드다. 지금 `traffic.wait_end` 에는 이유와 초만 있어 "어느 존에서" 기다렸는지 모른다. 혼잡 예측 라벨의 전제 조건이라 11월 중 선행 작업이다.
- DR-08 분량(존 대기 3,000건 등)은 추정치이고 baseline 야간 수집 후 다시 정한다.
- DR-09: CPU 90% 를 넘은 운행은 무효로 버린다. 시뮬레이터가 실시간으로 돌아서 PC 가 느려지면 대기시간 자체가 바뀌기 때문이다.

Q: 3,000건이면 충분한가?
A: 회귀 트리(gradient boosting)는 수천 건으로 학습되는 모델이라 골랐습니다. LSTM 은 데이터가 충분할 때만 비교합니다.

## 2.3 | AI학습서버의 요구사항
> 세 모델 모두 표 형식 특징과 짧은 시계열이라 CPU 로도 학습됩니다. 학과 GPU 서버를 기본으로 하되 늦어지면 팀원 PC·Colab 으로 대체합니다.

## 표 2.4 | AI학습 환경 및 AI 모듈 개발 기능
> 데이터 수집(1~3), 데이터셋(4~8), 혼잡·배터리·이상 학습(9~15), 평가·모델 카드(16~17), FMS 안의 추론 모듈(18~21)로 21개 작업을 나눴습니다.

모든 행이 "계획"이다. 행마다 담당자를 적어 누가 무엇을 내는지 분명히 했다. (21) 타임아웃·예외 시 규칙 값 대체가 AI 장애를 관제 장애로 번지지 않게 하는 핵심 장치다.

Q: 추론 서버를 따로 두지 않는 이유는?
A: 추론이 1ms 수준이라 네트워크 왕복이 더 비싸고, FMS 가 단일 프로세스 전제라 FMS 안에서 함수로 부르는 것이 가장 단순합니다(4.4절).

## AI 학습모델 요구사항 | AI 학습모델 요구사항
> AR-01~10 은 "모델이 무엇을 내야 하고, 어느 수준이면 쓰는가"입니다.

## 표 2.5 | AI 모델 요구사항 AR-01~10
> 혼잡은 규칙 대비 MAE −20%, 배터리는 MAE 5%p, 이상 탐지는 탐지율 90%·오경보 5%·지연 60초, 추론은 p95 20ms 입니다.

- AR-06: 이상 점수는 점검 "후보"로만 보인다. 로봇을 자동으로 서비스에서 빼지 않는다. 오경보 한 번에 멀쩡한 로봇이 빠지는 것을 막기 위해서다.
- AR-09: 미래 정보 누출 금지는 코드 리뷰 체크리스트로 강제한다(3.3절).

## 2.4 | AI서비스 유스케이스 모델
> 사람 액터(운영자·관리자), 외부 시스템(로봇·브로커·승강기·외부 시스템·러너·학습 환경), 시스템 타이머로 나눴습니다.

## 액터 정의 | 액터 정의
> 운영자와 관리자는 같은 화면을 쓰고 API 키 역할(viewer/operator/admin)로 권한이 나뉩니다.

## 표 2.6 | 액터
> 로봇은 "외부 시스템"입니다. FMS 는 로봇을 시뮬레이션하지 않고 MQTT 로 받은 보고만 봅니다.

타이머(1초 배정 루프)를 액터로 둔 이유: 배정·교통 안전·재경로·배터리·예약 실행·알림이 사람 조작 없이 매초 일어나므로 유스케이스의 주체로 보는 편이 자연스럽다.

## 그림 2.2 | 운영자 유스케이스
> 운영자는 작업 게시·취소, 실시간 관제, 로봇 조작, 알림·통계·이력을 다루고, 주황색 존별 대기·점검 후보·비교 화면이 이번 개발입니다.

## 그림 2.3 | 관리자 유스케이스
> 관리자는 현장·맵·구역·목적지·로봇·승강기·운영 정책·인증을 관리합니다.

include 관계: 맵 업로드는 항상 검증·굽기를 포함하고, 구역 저장은 새 맵 버전 생성과 SET_MAP 전파를 포함한다.

## 그림 2.4 | FMS 자동 처리 · AI 유스케이스
> 타이머가 매초 배정·통행 허가·교착 감지·충전을 돌리고, 이번 개발에서 예상 대기 계산·이상 점수·장애 재배정이 붙습니다.

## 유스케이스 명세 | 유스케이스 명세 UC-01~08
> 핵심 유스케이스 8개만 사전 조건·기본 흐름·대안 흐름·사후 조건으로 적었고, 나머지는 기능 표와 시퀀스에서 다룹니다.

발표에서는 UC-02(점유 존 통행 허가)만 자세히 말한다. 다섯 단계(층 정원 → 대기 node 예약 → 존 진입 → 출구 통과·차체 이탈 확인 → 층 허가 반납)가 이 시스템의 핵심이다.
- UC-02 대안 3b: 대기 node 앞을 유휴 로봇이 막고 있으면 그 로봇을 가까운 주차 지점으로 보낸다(60초에 1회). 이벤트 `staging.requested` 의 reason "비켜주기"가 이것이다.
- UC-04 대안 3a: 장애 로봇이 존 안이면 그 존은 "확인 필요"로 남는다. 다른 로봇은 우회하거나 기다린다.

Q: UC-03 에서 AI 가 경로를 정하면 허가 규칙과 충돌하지 않나?
A: AI 는 "어느 통로 순서로 갈지"만 정하고, 실제 진입 허가는 UC-02 규칙이 그 순간의 점유로 판단합니다. 역할이 분리돼 있습니다.

## 2.5 | 요구기능 정의 (웹사용자용)
> 운영자 기능 18개 중 존별 대기·점검 후보·비교 화면이 이번 개발이고, API 키 입력은 지금 브라우저 입력창이라 "부분"입니다.

## 표 2.7 | 운영자 요구기능 FR-U-01~18
> 각 기능에 화면 ID·API 그룹·상태·담당을 붙였습니다.

FR-U-02 의 "서버 미연결·상태 미수신·오래된 값 구분"은 실제 운영에서 중요하다. 화면의 로봇이 멈춰 보일 때 진짜 멈춘 것인지 데이터가 안 오는 것인지 운영자가 구분할 수 있어야 한다.

## 2.6 | 요구기능 정의 (웹관리자용)
> 관리자 기능 15개 중 통로 선택 정책(FR-A-07)과 MQTT 인증(FR-A-15)이 이번 개발입니다.

## 표 2.8 | 관리자 요구기능 FR-A-01~15
> 현장·맵·목적지·구역·교통·로봇·승강기·운영 정책·인증·webhook 을 관리합니다.

FR-A-05 구역 편집은 점유 존 외에 주행 금지, 감속, 일방통행, 자동문, 승강기 칸을 한 편집기에서 다룬다. 저장하면 새 맵 버전이 되고 로봇에 SET_MAP 으로 전달된다.

FR-A-15 MQTT 인증은 배포 전 필수다. 지금 브로커는 익명 접속 허용(개발용)이라 외부에 열면 누구나 로봇에 정지·취소를 보낼 수 있다.

## FMS 자동 처리 · AI · 실험 요구기능 | 시스템 요구기능
> 사람이 누르지 않아도 FMS 가 스스로 하는 일, AI, 실험 기능을 따로 묶었습니다.

## 표 2.9 | 시스템 요구기능 FR-S · AI · FR-E
> 배정·점유 존·층 정원·교착 감지·재경로·충전·승강기는 구현, 예상 대기 비용·장애 재배정·운행 기록·AI 네 종·러너·이상 주입·데이터셋이 이번 개발입니다.

- FR-S-01 배정 순서: (−우선순위, 생성 시각) — 우선순위가 높고 먼저 온 작업부터.
- FR-S-05 stall 기준: 이동 중 60초 동안 0.3 m 미만 이동, 또는 대기 180초 초과(코드 상수 `STALL_*`).
- FR-S-06 재경로: 같은 자리 30초 이상 보인 장애물을 맵에 5분 등록하고, 15초 이상 막히면 다른 gate 순서로 다시 계획(작업당 3회).
- AI-01 만 **필수**다.

## 2.7 | 비기능 요구사항
> 지연·처리량·장애 감지·재시작 복구·장기 안정성·안전 측 실패·테스트·보안·재현성·호환성·사용성 12개입니다.

## 표 2.10 | 비기능 요구사항 NFR-01~12
> 숫자가 있는 요구는 모두 측정 방법을 같이 적어 9장 시험으로 이어지게 했습니다.

- NFR-07 "안전 측 실패"가 통행권 방식의 장점이다. order 메시지가 유실되면 로봇은 추가 허가를 못 받아 멈출 뿐 위험 구역에 들어가지 않는다. 시험에서는 브로커 앞 프록시로 order 10% 를 일부러 버려 확인한다.
- NFR-05 재시작 복구 100%: 상태가 모두 원자적으로 교체되는 JSON 파일이라 가능하다.
- NFR-12: 빌드 도구·CDN 없이 동작해야 학교·현장 망에서도 열린다.

Q: 500ms 지연 목표는 어떻게 재나?
A: 로봇 State 의 timestamp 와 브라우저가 WebSocket 메시지를 받은 시각을 비교합니다. 같은 PC 시계를 쓰는 LAN 환경에서 잽니다.

## +표 2.10 | 비기능 요구사항 (이어짐)
> 호환성과 사용성 두 항목입니다. JSON 필드를 추가할 때는 기본값을 둬서 예전 파일이 그대로 읽히게 하고, 화면은 빌드·CDN 없이 1366px 이상에서 한국어로 동작해야 합니다.

호환성(NFR-11)은 이번 개발에서 jobs.json 에 run_id, traffic.json 에 route_policy 를 더할 때 특히 중요하다. 기본값이 없으면 기존 현장 데이터를 읽다가 서버가 뜨지 않는다. pytest 로 예전 형식 파일을 읽는 시험을 둔다.

## 2 | 심화 질의응답 — 요구사항
Q: 요구사항이 너무 많은데 우선순위는?

Q: 운영자와 관리자를 같은 화면으로 둔 것이 보안상 문제는 없나?
A: 권한은 화면이 아니라 서버 API 에서 역할로 검사합니다(표 7.10). 화면은 편의상 버튼을 비활성화할 뿐이라, 화면을 우회해 API 를 직접 불러도 역할이 없으면 403 입니다.
Q: NFR 수치(500ms, 200ms 등)의 근거는?
A: 제안서 33쪽 목표를 그대로 받았습니다. 로봇 State 주기가 200ms 라 화면 반영이 그 두세 배 안이면 운영자가 지연을 느끼지 않는다는 판단입니다. LAN 기준이며 배포 환경에서는 다시 잽니다.
Q: 유스케이스가 8개뿐인데 충분한가?
A: 핵심 흐름 8개만 명세로 쓰고, 나머지 기능은 요구기능 표(2.5~2.6)와 시퀀스 22종, 알고리즘 절(6.6)에서 더 자세히 다룹니다. 같은 내용을 세 번 쓰지 않으려는 선택입니다.
