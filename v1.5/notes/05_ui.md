## 5 | 5장 화면(UI) 설계
> 웹 관제 화면은 FMS 가 직접 내려주는 단일 페이지이고, 빌드 도구·CDN 없이 HTML/JS/Canvas 만 씁니다. 이 장의 화면은 실제 FMS 에 시뮬레이터 로봇 4대를 붙여 찍은 캡처이고, 이번 개발 화면 5종만 주황 점선 와이어프레임입니다.

화면 설명 방식: 캡처 위 주황 번호 → 아래 표의 같은 번호 설명. 발표에서는 모든 번호를 읽지 말고 화면마다 "이 화면에서 운영자가 하는 일 한 가지"만 말한다.

Q: 왜 React 를 쓰지 않았나?
A: 설비 관제 화면은 공장·학교 망처럼 외부 CDN 이 막힌 곳에서도 열려야 하고, 서버 하나만 배포하면 끝나는 편이 운영이 쉽습니다. 화면 규모(3.6k줄)도 빌드 도구 없이 관리할 수 있는 크기입니다.

## 5.1 | 사용자 메뉴구성
> 메뉴는 상황 관제·작업 운영·인프라·운영 분석·설정 다섯 그룹이고, 화면 ID 는 SC-00~SC-18 입니다.

## 표 5.1 | 메뉴와 화면 ID
> 운영자와 관리자는 같은 화면을 쓰고, 권한은 버튼이 부르는 API 의 역할 검사로 나눕니다. GET 은 viewer, 그 밖은 operator, 키·webhook·현장 삭제는 admin 입니다.

화면을 역할별로 따로 만들지 않은 이유: 권한 검사를 서버 한 곳(`auth.py`)에만 두면 화면에서 버튼을 숨기는 실수가 있어도 서버가 막는다. 화면은 편의로만 버튼을 비활성화한다.

## 그림 5.1 | SC-02 주 메뉴
> 왼쪽 메뉴에서 페이지를 바꾸고, 주소 뒤 #페이지 로 바로 열 수 있으며, 아래쪽에 서버·MQTT 연결 상태가 보입니다.

⑥ 연결 표시는 `/health` 를 주기적으로 불러 만든다. 운영자가 "로봇이 멈췄다"고 오해하기 전에 "서버 연결 끊김"을 먼저 보게 하는 장치다.

## 5.2 | 초기화면(로그인 전환면) 설계
> 사용자 계정 대신 API 키로 인증합니다. 인증이 켜진 서버에 처음 들어오면 키 입력 화면(SC-00)이 나옵니다. 지금은 브라우저 입력창이라 이번 개발에서 페이지 안 화면으로 바꿉니다.

계정·비밀번호 대신 키를 쓰는 이유: 관제 서버의 주 사용자는 사람보다 외부 시스템(WMS, 실험 러너, 스크립트)이다. 사람과 도구가 같은 방식으로 인증받는다.

- WebSocket·맵 이미지처럼 헤더를 붙일 수 없는 요청은 `?api_key=` 로 키를 보낸다(구현됨).
- 키는 해시로만 저장하고 발급할 때 한 번만 보여 준다.

Q: 키가 유출되면?
A: SC-12 에서 그 키를 폐기하고 새 키를 발급합니다. 키마다 이름이 있어 이벤트 로그의 actor 로 누가 무엇을 했는지 추적됩니다.

## 5.3 | 사용자 화면설계 (웹)
> 운영자 화면은 실시간 맵, 로봇, 알림, 작업 게시판, 프리셋, 통계, 이력이고, 존별 대기·점검 후보·비교 화면이 추가됩니다.

## SC-01 | SC-01 실시간 맵
> 운영자가 가장 오래 보는 화면입니다. 로봇의 실제 크기·방향·상태색, 구역(금지·점유 존·자동문), 목적지, 남은 경로가 한 장에 보입니다.

## 그림 5.3 | SC-01 실시간 맵
> 점유 존은 상태색이 바뀝니다. 비어 있음 초록, 예약 파랑, 점유 중 진파랑, 확인 필요 빨강입니다.

- ⑥ "확인 필요"(빨강)는 로봇이 존 안에서 통신이 끊기거나 오류가 나 퇴장 증거가 없는 상태다. 운영자가 현장을 확인해야 풀린다. 시간이 지났다고 자동으로 풀지 않는 것이 안전 원칙이다.
- ⑦ 로봇 아이콘은 Factsheet 의 실제 크기로 그린다. 좁은 통로에서 차체가 존에 걸쳤는지 눈으로 볼 수 있다.
- 로봇 위치는 WebSocket(WS-01)으로 바뀐 로봇만 받는다. 새로고침 ③은 맵·목적지·작업만 다시 읽는다.

## 그림 5.4 | SC-01 로봇 팝업
> 로봇을 누르면 연결 상태, 표시 상태, 배터리, 현재 작업과 대기 이유, 위치 추정, 조작 버튼, 통행권 상세가 나옵니다.

- ④ 대기 이유("점유 존 Z1 대기 · 앞 2대")가 운영자에게 가장 쓸모 있는 정보다. 이번 개발에서 존 ID 와 예상 대기를 덧붙인다.
- ⑥ 로봇에서 직접 건 일시정지(LOCAL)는 FMS 가 풀 수 없어 [재개]가 비활성이다. 현장 작업자가 로봇을 세웠는데 관제실에서 풀어 버리면 위험하기 때문이다(프로토콜 규칙).
- ⑦ "허가 노드 수"와 "order_update_id"는 디버깅용이다. 통행권이 어디까지 나갔는지 보인다.

## SC-15 | SC-15 존별 대기 패널 (계획)
> 3단계 시연에서 "AI 가 왜 우회를 골랐는지" 보여 주는 화면입니다. 존마다 대기열, 최근 평균 대기, 예상 대기와 출처(AI/규칙), 예약된 통과 수를 보입니다.

⑧ "최근 경로 선택"이 발표의 핵심 장면이다. "주 통로 이동 18초 + 대기 52초 vs 우회 이동 41초 + 대기 9초 → 우회"처럼 비교 근거가 숫자로 보인다. 데이터는 이번 개발의 `route.choice` 이벤트에서 온다.

! 와이어프레임 안 숫자는 예시다. 실측처럼 말하지 않는다.

## SC-03 | SC-03 로봇
> 로봇 등록·목록·상세·재배정·점검 전환·그룹을 다루는 화면입니다.

## 그림 5.5 | SC-03 로봇 목록
> 등록 즉시 SET_MAP 이 나가고, 목록의 "맵 동기화" 열로 로봇이 배정 맵의 같은 버전을 쓰는지 봅니다.

⑥ 미등록 로봇: MQTT 로 보고는 오는데 이 현장에 등록되지 않은 로봇이다. 새 로봇을 켜면 여기 먼저 나타나 [등록]으로 받아들인다.

Q: 등록 해제를 막는 경우는?
A: 그 로봇에 교통 예약이 남아 있으면 막습니다. 예약이 남은 채 지워지면 그 존이 영원히 점유 상태로 남기 때문입니다.

## 그림 5.6 | SC-03 로봇 상세 대화상자
> 실시간 맵 밖(로봇 목록·알림 등)에서도 같은 로봇 상세를 대화상자로 봅니다. 내용은 팝업과 같습니다.

## SC-04 | SC-04 알림
> 상태 규칙(연결 끊김·오류·배터리 위험·교착 등)과 사건 규칙(작업 실패·마감 초과)으로 열린 알림을 보고 확인합니다.

## 그림 5.7 | SC-04 알림
> 상태 규칙 알림은 조건이 사라지면 스스로 해소되고, 사건 규칙 알림은 운영자가 확인하면 해소됩니다.

같은 key(예: `robot_offline:AMR-002`)의 알림은 하나만 열려 있다. 같은 로봇이 계속 끊겨도 알림이 폭주하지 않는다. ⑤ [로봇 이력]은 SC-14 이력 화면을 그 로봇으로 필터해 연다.

## SC-16 | SC-16 점검 후보 (계획)
> 이상 탐지가 연속 3창 임계를 넘은 로봇을 근거와 함께 보이고, 운영자가 점검 전환이나 무시를 고릅니다.

④ 열 "정상 대기와 비교"가 이 화면의 핵심이다. AMR-004 처럼 허가 없이 대기 node 에 서 있는 로봇은 점수가 낮고 경보하지 않는다. AMR-007 처럼 허가를 받았는데 안 움직이면 점검 후보다. 제안서 28쪽 그림과 같은 구분이다.

## 표 5.2 | 근거 특징 → 표시 문구
> 모델의 재구성 오차 상위 특징을 운영자가 읽을 수 있는 문장으로 바꿉니다.

"재구성 오차"는 운영자에게 의미가 없다. "허가 노드 3개 남음 · 위치 변화 0.02 m"처럼 현장 언어로 바꿔야 판단에 쓸 수 있다.

## SC-05 | SC-05 작업 게시판
> 작업을 만들고, 게시판·실행 중·이력 탭으로 상태를 보고, 취소·재시도·수동 배정을 합니다.

## 그림 5.8 | SC-05 작업 게시판 — 배정·실행 중 탭
> 프리셋을 고르고 배정 방식·우선순위·그룹·시작 시각·마감을 정해 [작업 생성]을 누르면 1초 안에 로봇이 배정됩니다.

- ⑨ 진행률은 "완료 명령 수 / 전체"다. FMS 가 끼워 넣은 대기·출구 node 는 사용자 명령이 아니라 진행률에서 뺀다.
- ⑩ 대기 이유는 배정을 못 하는 이유("배정할 로봇 없음: 배터리 부족")와 교통 대기 이유("점유 존 대기", "층 정원 대기")를 모두 보인다.
- ⑥ 시스템 작업(충전·대기 복귀·대피·복구)은 기본으로 숨긴다. 운영자가 만든 작업만 보이게 하려는 것이다.

## 그림 5.9 | SC-05 작업 이력 탭
> 끝난 작업은 성공·실패·취소로 남고, 실패 사유(예: COLLISION)와 [재시도]가 있습니다. 재시도는 새 작업을 만들고 원래 작업을 retry_of 로 가리킵니다.

종료된 작업의 상태를 바꾸지 않고 새 작업을 만드는 이유: 이력이 바뀌지 않아야 KPI(성공률·실패 사유)가 정확하다.

## SC-06 | SC-06 작업 프리셋 · 예약 실행
> 자주 쓰는 작업을 단계 목록으로 저장하고, 요일·시각이나 간격으로 자동 게시합니다.

## 그림 5.10 | SC-06 작업 프리셋
> 단계는 이동·대기·적재·하차·도킹·주차 여섯 종입니다. 프리셋을 고쳐도 이미 만든 작업에는 영향이 없습니다(게시 시점 스냅샷).

⑧ 서버가 꺼져 있던 동안 놓친 예약 회차는 몰아서 실행하지 않고 건너뛴다. 재시작 직후 작업이 폭주하는 것을 막는다.

## SC-13 | SC-13 통계
> 최근 24시간·14일 기준으로 완료·성공률·배정 대기·수행 시간·가동률·주행 거리·교통 대기·승강기 대기·마감 초과를 봅니다.

## 그림 5.11 | SC-13 통계
> KPI 는 전부 이벤트 로그에서 계산합니다. 별도 집계 테이블이 없어 이벤트만 정확하면 통계도 정확합니다.

⑥ 로봇별 표 아래에 이번 개발에서 "존별 대기 표"(존·횟수·평균·최대·p95)와 운행(run_id) 선택을 추가한다. 실험 결과를 이 화면에서 바로 확인하려는 것이다.

Q: 성공률에서 시스템 작업을 빼는 이유는?
A: 충전·대기 복귀 같은 FMS 내부 작업이 섞이면 운영자가 만든 작업의 성공률이 왜곡되기 때문입니다.

## SC-17 | SC-17 관제 방식 비교 · 시연 (계획)
> 실험 운행 두 개를 골라 병목 대기·시간당 완료·교착·미완료·허가 없는 진입을 나란히 봅니다.

③ "대기를 줄였어도 실패·교착이 늘면 함께 표시"는 제안서의 평가 원칙이다. 한 지표만 좋아 보이게 하지 않는다. 그래프는 빌드 없이 Canvas 로 그린다.

! 화면의 −15.0%, +5.2% 는 예시 값이다.

## SC-14 | SC-14 이력
> 분류·심각도·로봇·작업으로 이벤트를 필터해 봅니다. 장애 원인을 거꾸로 따라갈 때 쓰는 화면입니다.

## 그림 5.12 | SC-14 이력
> 이벤트 이름은 한국어로 보이고, 내용 열은 이벤트 data 를 요약합니다. 조작자 열에 API 키 이름이 남아 누가 무엇을 했는지 보입니다.

## 5.4 | 관리자 메뉴구성
> 관리자도 같은 메뉴를 쓰고, 설정을 바꾸는 화면과 그 화면이 바꾸는 파일을 표로 정리했습니다.

## 표 5.3 | 관리 대상과 바뀌는 데이터
> 화면 하나가 파일 하나를 바꾸도록 나눴습니다. 설정 변경은 모두 이벤트 로그에 조작자와 함께 남습니다.

이 표가 8장 데이터 설계와의 연결 고리다. "이 화면에서 저장하면 어느 파일이 바뀌나"를 물으면 이 표로 답한다.

## 5.5 | 관리자 화면설계 (웹)
> 구역 편집기, 맵 관리, 목적지, 운영 제어, 엘리베이터, 현장 설정, AI 정책 카드입니다.

## SC-07 | SC-07 구역 편집기 (점유 존)
> 실시간 맵 위에 겹쳐 여는 편집기입니다. 사각형을 그리고 회전하고, 진입 방향마다 대기 node 와 출구 node 를 고릅니다.

## 그림 5.13 | SC-07 구역 편집기
> 구역 종류는 주행금지·엘리베이터·점유 존·일방통행·자동문·감속 여섯 가지이고, 저장하면 새 맵 버전이 활성화돼 로봇에 전달됩니다.

- ④ 회전은 실제 회전된 경계로 겹침·차체 이탈을 판단한다(축 정렬 사각형으로 근사하지 않음). 기하 계산은 브라우저와 서버가 같은 규칙을 쓰고 node 테스트(`zone-geometry.test.js`)로 확인한다.
- 일방통행은 진입 방향을 1개만 둔 점유 존, 자동문은 문 진입점 2개를 가진 점유 존으로 저장한다. 로봇 입장에서는 모두 "점유 존"이다.

## 표 5.4 | 구역 편집 검증
> 크기, 맵 범위, 다른 존과의 겹침, 대기·출구 node 의 차체 여유, 동시 편집, 남은 교통 예약을 검사합니다.

- "다른 사람이 먼저 편집"은 `base_version` 낙관적 잠금이다. 두 관리자가 동시에 편집해도 나중 저장이 앞의 변경을 덮어쓰지 않는다(409).
- "교통 예약이 남아 있으면 거절": 로봇이 존 안에 있는데 존 모양을 바꾸면 퇴장 판정이 깨진다.

## SC-08 | SC-08 맵 관리
> 맵을 올리면 검증하고, 주행 금지 영역을 굽고, 내용 해시로 버전을 만듭니다. 버전을 골라 활성화할 수 있습니다.

## 그림 5.14 | SC-08 맵 관리
> 맵 식별자는 셋입니다. 사람이 붙인 map_id, 로봇이 보고하는 map_uid, 내용 해시 version 입니다.

로봇은 배정 맵의 uid 와 활성 version 을 보고해야 작업을 받는다. 맵이 다른 로봇에 작업을 주면 엉뚱한 좌표로 가기 때문이다. 벤더 SLAM 맵(`grid_cfg.grid`)도 바로 올릴 수 있다.

## SC-09 | SC-09 목적지 · 도킹
> 이름 붙은 위치(작업 지점·충전기·주차·대기/출구 node·픽업·반납)를 등록합니다.

## 그림 5.15 | SC-09 목적지 · 도킹
> 이름을 바꾸면 프리셋과 아직 배정 안 된 작업의 참조도 같이 바뀌지만, 이미 만든 작업의 좌표 스냅샷은 그대로입니다.

저장할 때 주행 불가 칸(벽·금지 구역)이면 거절한다. 로봇이 갈 수 없는 목적지를 미리 막는다.

## SC-10 | SC-10 운영 제어
> 현장 정지·대피와 자동 충전·대기 복귀 정책을 다룹니다.

## 그림 5.16 | SC-10 운영 제어
> 현장 정지는 전 로봇 일시정지와 배정 중지, 대피는 진행 작업을 취소하고 제자리 정지 또는 주차 지점으로 이동입니다.

- 정지·대피는 로봇을 세울 뿐 교통 예약과 승강기 임대를 풀지 않는다. 세운다고 존에서 나간 것은 아니기 때문이다.
- ⑥ 충전 기준 기본값: 충전 시작 25%, 위험 알림 10%, 충전 완료 60%, 작업 수락 최소 20%. 서버는 "위험 ≤ 시작 < 완료", "작업 수락 최소 < 완료" 순서를 검사한다.

Q: 정지 상태에서 서버를 재시작하면?
A: 정지 상태는 `site.json` 에 저장돼 재시작 후에도 유지됩니다. 재시작했다고 로봇이 다시 움직이지 않습니다.

## SC-11 | SC-11 엘리베이터
> 층마다 같은 승강기에 해당하는 구역을 묶어 승강기를 만들고, 운행 상태와 칸 안 로봇 복구를 봅니다.

## 그림 5.17 | SC-11 엘리베이터
> 승강기는 FIFO 로 임대하고, 고장이면 예비 승강기로 바꾸며, 칸 안에서 문제가 생기면 "확인 필요"로 표시해 운영자가 하차·임대 해제를 합니다.

시연은 FMS 내장 승강기 시뮬레이터로 한다. 실제 승강기는 같은 MQTT 계약(`elev/v1/{id}`)만 맞추면 붙는다.

## SC-12 | SC-12 현장 설정
> 선택 맵의 교통 제어(층 정원·경로 교차 정지), 교통 상태, 현장, 인증, webhook, API 키를 한 화면에서 다룹니다.

## 그림 5.18 | SC-12 현장 설정
> ⑤ 교통 상태 카드에 정체·교착·존 상태·로봇별 이동 허가가 보여 교통 문제를 이 화면에서 진단합니다.

- ② 층 정원(동시 이동 허가 대수)을 비우면 무제한이다. 정원을 줄이면 혼잡은 줄지만 처리량도 준다. 실험 변수로 쓸 수 있다.
- ⑨ API 키는 발급 때 한 번만 보여 준다. 마지막 admin 키는 지울 수 없다(자기 자신을 잠그는 것을 막음).

## SC-18 | SC-18 통로 선택 정책 · AI 모델 카드 (계획)
> 실험 조건 ②③④를 설정 한 번으로 바꾸고, FMS 가 지금 읽은 모델과 대체 횟수를 보여 줍니다.

④~⑥ 은 "AI 가 지금 실제로 쓰이고 있는가"를 증명하는 카드다. 호출 수 대비 대체 수가 많으면 AI 결과가 아니라 규칙 결과로 실험한 셈이라, 실험 운행마다 이 값도 기록한다.

## 5.6 | 메시지 · 오류 화면 설계
> 성공은 아래 토스트 3초, 실패는 빨간 토스트와 입력칸 강조, 위험한 조작은 확인 대화상자를 먼저 띄웁니다.

## 표 5.5 | 공통 상태 표시
> 서버 끊김, MQTT 끊김, 로봇 상태 미수신, 오래된 값, 401/403 을 화면마다 같은 방식으로 보입니다.

"오래된 값(3초↑)"은 FMS 의 STALE 판정 기준(3초)과 같다. 화면과 서버가 같은 기준을 써야 혼란이 없다.

## 표 5.6 | 주요 성공 메시지
> 실제 코드에 있는 문구를 그대로 옮겼습니다.

## 표 5.7 | 주요 오류 메시지
> 오류 문구는 서버가 만들고 화면은 받은 문구를 그대로 보입니다. 화면과 서버에 같은 검증을 두 번 짜지 않기 위해서입니다.

오류 코드 규칙: 대상 없음 404, 검증 실패 422, 상태·버전 충돌 409. 예를 들어 "로봇이 바쁘다"는 409(지금 상태 때문), "배터리 부족"은 422(요청이 규칙에 맞지 않음)다.

## +그림 5.10 | SC-06 프리셋 화면 설명 (이어짐)
> 프리셋 만들기 카드, 단계 편집, 목록, 예약 실행 카드의 번호 설명입니다.

③ 단계 종류별 입력: 이동은 목적지, 대기는 초, 적재·하차는 payload_id, 도킹·주차는 충전소·주차 지점. 프리셋 저장 시 목적지가 실제로 있는지 서버가 검사한다.
⑥ [게시판으로]를 누르면 SC-05 가 그 프리셋을 고른 채 열린다. 프리셋 화면에서 바로 작업을 만들지 않고 게시판에서 배정 방식·우선순위를 정하게 한 것이다.

## 그림 5.2 | 화면 흐름도 (v1.5 신설)
> 모든 화면은 주 메뉴에서 바로 열리고, 화면 사이는 버튼으로 이어집니다. 이번 개발 화면 다섯 개는 메뉴를 늘리지 않고 기존 화면의 패널·탭·카드로 붙입니다.

흐름도에서 보여 줄 경로 두 개: ① 실시간 맵 → 로봇 클릭 → 팝업 → [이력] → 그 로봇으로 걸러진 이력. ② 알림 → 점검 후보 → [점검 전환] → 로봇 목록에서 점검 중. 운영자가 "이상하다 → 원인 확인 → 조치"를 세 번의 클릭 안에 할 수 있게 한 것이 설계 의도다.

Q: 새 화면을 메뉴로 따로 두지 않은 이유는?
A: 운영자가 이미 보는 화면 옆에 정보가 있어야 쓰입니다. 존별 대기는 지도를 보면서, 점검 후보는 알림을 보면서 확인하는 것이 자연스럽습니다.
