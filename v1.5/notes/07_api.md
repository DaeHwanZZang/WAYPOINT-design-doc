## 7 | 7장 API 설계
> FMS 의 외부 인터페이스는 세 갈래입니다. 웹·외부 시스템과는 REST·WebSocket, 로봇·승강기·자동문과는 MQTT, 로봇의 맵 다운로드는 HTTP 파일입니다. 내부 모듈은 함수 API, 학습 파이프라인은 파일 API 로 연결됩니다.

이 장의 표 대부분은 코드에서 자동 생성했다(MQTT 는 `common/schemas.py`, REST 는 FMS 의 OpenAPI). 손으로 옮겨 적지 않아 코드와 문서가 어긋나지 않는다는 점을 먼저 말한다.

## 7.1 | 서버/클라이언트 구조
> 로봇과의 계약은 MQTT 메시지 다섯 종(Order, InstantAction, State, Connection, Factsheet)이고, VDA 5050 의 개념을 따랐습니다.

## 그림 7.1 | 서버/클라이언트 통신 구조
> 브로커가 가운데 있어 FMS 와 로봇은 서로의 주소를 몰라도 됩니다. 로봇이 죽으면 브로커가 대신 "연결 끊김"(LWT)을 알립니다.

## MQTT 토픽 (외부 모듈 인터페이스 — 로봇·설비) | MQTT 토픽
> 토픽 이름은 fms/v1/{로봇 ID}/{종류} 규칙이고, 승강기는 elev/v1, 자동문은 door/v1 입니다.

## 표 7.1 | MQTT 토픽
> State 는 QoS 0 으로 200ms 마다, 나머지는 QoS 1 입니다. Connection 과 Factsheet 는 retained 라 FMS 가 늦게 켜져도 마지막 값을 바로 받습니다.

- State 를 QoS 0 으로 둔 이유: 200ms 마다 새 값이 오므로 하나 잃어도 다음 것이 곧 온다. 재전송 부담을 줄인다.
- Order 는 QoS 1(최소 한 번). 같은 오더가 두 번 와도 order_update_id 로 걸러진다.
- 시뮬레이터 전용 InstantAction(INJECT_FAULT·장애물 주입)은 실험·시험용이다. 실제 로봇은 무시해도 된다.

Q: 프로토콜을 바꾸면 어떻게 동기화하나?
A: 원본은 AMR-fms `common/` 입니다. 뷰어 사본은 바이트 동일해야 하고 테스트(`test_common_sync.py`)가 검사합니다. C++ 은 수동 포팅이라 가장 위험해서, 바꾸는 순서를 정해 두었습니다(원본 → 사본 → C++ → 양쪽 커밋).

## MQTT 메시지 스키마 | MQTT 메시지 스키마
> 메시지마다 필드·타입·필수 여부·기본값·설명을 표로 옮겼습니다. 모든 메시지는 version·header_id·timestamp·robot_id 공통 헤더를 갖습니다.

## 표 7.2 | 로봇 메시지 필드
> header_id 는 보낸 쪽마다 하나씩 늘어나는 번호라 유실·순서 뒤바뀜을 검출할 수 있습니다.

## Order fms/v1/{id}/order FMS → 로봇 QoS 1 | Order
> 오더는 노드 목록입니다. 노드마다 released(가도 되는가)가 붙고, 같은 order_id 로 order_update_id 를 올려 다시 보내면 통행권이 넓어집니다.

## OrderNode (Order.nodes[]) | OrderNode
> 노드마다 위치, released, 허용된 점유 존 목록(allowed_zone_ids), 액션이 붙습니다.

`allowed_zone_ids` 가 로봇 쪽 안전장치다. 로봇은 A* 로 길을 찾을 때 허용 목록에 없는 점유 존을 벽처럼 피한다. FMS 가 허가하지 않은 존을 로봇이 "지름길"로 지나가는 일을 막는다.

`reserved_window`(시간창)는 v1.0 의 시공간 예약 흔적으로 계약에 남아 있지만 쓰지 않는다.

## Action (OrderNode.action) | Action
> 노드에서 할 일입니다. 적재·하차·충전·대기·직선 이동·도킹·주차 일곱 종이고, params 로 세부 값을 줍니다.

STRAIGHT 는 승강기·도킹처럼 경로 계획 없이 곧게 들어가야 하는 구간에 쓴다. 이 구간이 미허가 점유 존을 지나면 로봇이 TRAFFIC_BLOCKED 로 거절한다(표 8.19).

## InstantAction fms/v1/{id}/instant FMS → 로봇 QoS 1 | InstantAction
> 오더와 별개로 즉시 실행하는 명령입니다. 취소·일시정지·재개·오류 해제·맵 교체·위치 힌트와 시뮬레이터 전용 주입 명령이 있습니다.

## State fms/v1/{id}/state 로봇 → FMS QoS 0, 200ms | State
> FMS 가 로봇에 대해 아는 것은 전부 이 메시지에서 옵니다. 상태 4축, 추정 위치와 점수, 맵 ID·버전, 마지막 통과 노드, 노드별 허가 상태, 배터리, 오류, 적재, 감지 장애물, 남은 경로입니다.

- `last_node_id` + `node_states` 가 SD-02 해제 판단의 증거다.
- `localization_score` 와 `map_version` 이 맞지 않으면 배정하지 않는다.
- `local_path`(남은 경로)로 웹에 화살표를 그리고, 경로 교차 예고(conflict)를 계산한다.
- `detected_obstacles` 를 30초 이상 같은 자리에서 보이면 맵 장애물로 등록한다(재경로).

## NodeProgress (State.node_states[]) | NodeProgress
> 아직 지나지 않은 노드와 각 노드의 허가 여부입니다. 이상 탐지 특징 released_ahead 가 여기서 나옵니다.

## ActionProgress (State.action_states[]) | ActionProgress · BatteryInfo
> 액션마다 대기·실행·완료·실패 상태를 보고합니다. 도킹·충전 실패는 오류가 아니라 이 액션 상태의 FAILED 로 옵니다.

## ErrorInfo (State.errors[]) | ErrorInfo · LoadInfo · ObstacleInfo
> 오류는 WARNING 과 FATAL 두 단계이고, FATAL 이면 로봇이 오더를 버리고 ERROR 상태가 됩니다. 적재 칸과 감지한 장애물 사각형도 State 에 붙습니다.

## Connection fms/v1/{id}/connection 로봇(또는 브로커 LWT) → FMS QoS 1, retained | Connection
> 로봇이 접속하면 ONLINE, 정상 종료면 OFFLINE, 비정상 종료면 브로커가 미리 맡겨 둔 CONNECTION_BROKEN 을 대신 발행합니다.

LWT(Last Will)는 로봇이 접속할 때 "내가 갑자기 끊기면 이 메시지를 보내 달라"고 브로커에 맡겨 두는 MQTT 기능이다. 프로세스를 kill 해도 FMS 가 바로 안다. 장애 감지 3초 목표의 근거다.

## Factsheet fms/v1/{id}/factsheet 로봇 → FMS retained, 선택 | Factsheet
> 로봇의 정적 정보입니다. 크기·최고 속도·적재 칸 수·지원 액션·점유 존 지원 여부·적재 보고 여부입니다.

`traffic_control=false` 인 로봇(점유 존 경로 차단을 모르는 클라이언트)에는 점유 존 관제를 적용할 수 없다. 다른 벤더 로봇을 붙일 때 이 값을 먼저 본다.

## 표 7.3 | 열거형
> 상태·액션·오류 수준·연결·위치 추정·즉시 명령 열거형 값입니다. C++ 쪽 문자열과 정확히 같아야 합니다.

## MQTT 계약 변경 (이번 개발) | 이번 개발의 MQTT 변경
> 이번 개발에서 바꾸는 계약은 이상 주입 4종뿐이고, params 가 자유 dict 라 FMS 쪽 스키마는 바꾸지 않습니다.

## 표 7.4 | 이상 주입 4종
> 허가 후 정지, 점진적 속도 저하, 배터리 급소모, 위치 튐을 시뮬레이터에 주입하고 시각을 기록해 이상 탐지의 정답으로 씁니다.

- 기존 FATAL 주입은 "즉시 고장"이라 탐지할 필요가 없다(로봇이 스스로 보고). 이번 4종은 로봇이 스스로 알리지 않는 "조용한 이상"이라 AI 가 필요하다.
- 위치 튐은 추정 자세만 흔들고 실제 자세는 그대로라 물리 충돌은 생기지 않는다.
- 주입·해제 시각은 로봇 로그와 러너 기록 양쪽에 남겨 ±0.2초 정확도를 맞춘다(DR-05).

## 내부 모듈 인터페이스 (함수 API) | 함수 API
> 모듈끼리는 같은 프로세스의 함수로 부르며, 작업 상태를 바꾸는 호출은 모두 JobCoordinator.lock 안에서 합니다.

## 표 7.5 | 주요 함수 API FN-01~27
> FN-01~19 는 지금 있는 함수, FN-20~27 은 이번 개발 함수입니다. 이름과 시그니처를 미리 정해 담당자들이 동시에 개발할 수 있게 했습니다.

- FN-04 `rank_candidates` 는 후보가 없을 때의 "이유"도 돌려준다. 게시판의 "배정할 로봇 없음: 배터리 부족"이 여기서 나온다.
- FN-20·21 `RouteCostPolicy` 가 실험 조건 ②③④를 바꾸는 정책 객체다. traffic 과 assign 이 같은 정책 객체를 쓴다.
- FN-22 `fail_lost` 가 장애 자동 재배정의 함수다.

## 파일 API | 파일 API
> 로봇 맵 번들, FMS 상태 파일, 이벤트 DB, 운행 폴더, 데이터셋, 모델 폴더가 파일로 주고받는 인터페이스입니다.

## 표 7.6 | 파일 인터페이스
> 생산자와 소비자가 다른 파일마다 형식을 정했습니다. 맵 번들은 로봇이 받아 버전별로 캐시하고, 토큰이 있으면 URL 에 붙입니다.

로봇이 맵을 MQTT 가 아니라 HTTP 로 받는 이유: 맵 이미지는 수 MB 라 MQTT 메시지로 보내면 브로커에 부담이 크다. MQTT 로는 "새 맵이 있다 + URL"만 보낸다.

## 7.2 | 서비스 REST API 정의
> 기본 경로는 /api/v1, 요청·응답은 JSON, 인증은 Bearer API 키입니다. 오류는 404·422·409·401·403 규약을 따르고 본문은 {"detail": 메시지} 입니다.

## 표 7.7 | 구현된 REST API 목록
> 82개를 그룹 번호로 묶었습니다. 1xx 현장·맵·로봇, 2xx 목적지, 3xx 구역·교통, 4xx 작업·프리셋·충전, 5xx 로봇·운영, 6xx 승강기, 7xx 관측, 8xx 인증, 9xx 상태입니다.

권한 열: GET 은 대부분 viewer, 바꾸는 요청은 operator, 키·webhook·현장 삭제는 admin. 서버의 `/docs` 에서 같은 내용을 대화형으로 볼 수 있다.

## 표 7.8 | WebSocket
> 로봇 상태 스트림과 이벤트 스트림 두 개이고, 둘 다 서버에서 화면으로 한 방향입니다.

로봇 스트림은 접속하면 전체 목록을 한 번 보내고 이후 바뀐 로봇만 보낸다. 이벤트 스트림은 현장·종류로 걸러 받는다.

## 표 7.9 | 이번 개발에서 추가하는 REST API
> 교통 정책 필드, 존 예상 대기 필드, 운행 시작·종료·목록·요약, 이벤트 run_id 필터, 존별 KPI 를 추가합니다.

기존 API 에 필드를 더하는 것은 "확장"으로 표시했다(번호를 새로 쓰지 않음). 기존 클라이언트는 새 필드를 무시하면 되므로 하위 호환이다(NFR-11).

Q: 운행 시작 API 가 왜 필요한가? 러너가 시각만 기록하면 되지 않나?
A: FMS 이벤트에 run_id 를 직접 붙여야 운행이 끝난 뒤 정확히 그 운행의 이벤트만 꺼낼 수 있습니다. 시각으로 자르면 운행 경계에서 앞뒤 이벤트가 섞입니다.

## 7.3 | 서비스 REST API 설계
> 구현된 API 마다 경로·권한·오류·파라미터·요청·응답 필드를 적었습니다. 이 절은 발표 때 넘기고 질문이 오면 찾아보는 참고 자료입니다.

## API-101 | 현장 API (101~104)
> 현장은 FMS 데이터의 최상위 단위입니다. 맵·로봇·작업이 모두 현장 아래에 있습니다.

현장 삭제(104)는 admin 만 할 수 있고, 로봇이 등록돼 있으면 `force=true` 없이는 지우지 않는다(422). 지우면 그 현장 폴더(맵·작업 포함)가 통째로 사라지므로 시연 전에 조심한다.

## API-105 | 맵 업로드 (105)
> multipart 로 맵 파일을 올리면 검증·노이즈 정리·금지 구역 굽기·버전 생성을 한 번에 하고, activate 가 켜져 있으면 배정 로봇에 바로 알립니다.

응답의 `warnings` 에 좌표계 보정 같은 경고가, `stats` 에 굽기 통계가 담긴다. 같은 내용을 다시 올리면 같은 해시라 새 버전이 생기지 않는다.

## API-107 | 맵 조회 (106~110)
> 맵 목록·버전 목록·버전 메타·번들 zip·버전 파일을 조회합니다. 번들 zip(109)은 로봇이 SET_MAP 을 받고 내려받는 주소입니다.

맵 파일(110)은 웹이 실시간 맵 배경 이미지를 그릴 때 쓴다. 이미지 요청에는 헤더를 붙일 수 없어 `?api_key=` 로 인증한다.

## API-111 | 맵 버전 활성화 (111)
> 이전 버전으로 되돌릴 때도 이 API 를 씁니다. 교통 예약이 남아 있으면 막습니다.

## API-112 | 로봇 등록·변경·해제 (112~115)
> 로봇을 현장·맵에 등록하면 SET_MAP 을 보낸 결과(set_map_sent)까지 응답합니다. 변경(114)으로 맵 재배정·점검 전환·그룹을 바꿉니다.

점검 후보 화면(SC-16)의 [점검 전환]도 114 를 그대로 쓴다. 새 API 를 만들지 않는다.

## API-201 | 목적지 API (201~205)
> 이름 붙은 위치를 등록·조회·수정·삭제합니다. 응답에 그 맵의 map_uid 와 경고가 같이 옵니다.

수정(204)으로 이름을 바꾸면 프리셋과 아직 배정 안 된 작업의 참조도 같이 바뀐다.

## API-202 | 목적지 등록 세부
> type 은 station·charger·parking·waypoint·pickup·tray_return·other 이고, 대기·출구 node 는 waypoint 로 등록합니다.

## API-204 | 목적지 수정
> 경로 문자(/, ..)가 들어간 이름은 거절합니다. 이름이 파일 경로나 URL 에 쓰이기 때문입니다.

## API-206 | 맵 위에서 위치 추가 (206~207)
> 실시간 맵의 ＋ 메뉴에서 찍은 위치를 바로 등록합니다. 맵 버전 안에 들어가는 위치라 base_version 을 받습니다.

충전·도킹 지점(207)은 진입 방향(entry)까지 받아 로봇이 어느 쪽에서 들어가 도킹할지 정한다.

## API-208 | 픽업스테이션 (208~211)
> 픽업 구역과 픽업·반납 지점을 한 번에 만들고 고칩니다. 목록 응답에 연결 상태(ok/broken)가 있어 지점이 지워지면 바로 보입니다.

## API-301 | 구역 생성·수정·삭제 (301~303)
> 구역을 바꾸면 항상 새 맵 버전이 만들어지고 활성화됩니다. 점유 존은 gates(진입 방향별 대기·출구)를, 자동문은 door_id·door_nodes 를, 감속 구역은 speed_limit 를 받습니다.

x·y·width·height·rotation 으로 사각형을 받고, 서버가 회전된 꼭짓점(polygon)으로 바꿔 저장한다.

## API-304 | 교통 상태 조회 (304)
> 층 정원, 로봇별 이동 허가, 교통 예약, 존 상태, 대기 작업, 교착·정체, 맵 장애물을 한 번에 줍니다. 이번 개발에서 존별 예상 대기(forecast)를 더합니다.

## API-305 | 교통 설정 (305)
> 층 동시 이동 대수와 경로 교차 정지 옵션을 바꿉니다. 이번 개발에서 route_policy 와 assign_wait 를 더해 실험 조건을 바꿉니다.

## API-401 | 작업 생성 (401)
> 프리셋 없이 명령 목록으로 작업을 만듭니다. 외부 시스템은 external_id 를 붙여 같은 주문을 두 번 보내도 한 번만 만들어지게 합니다.

robot_id 를 주면 그 로봇 직접 지정, auto_assign=false 면 게시판에만 올린다. not_before 전에는 배정하지 않고, deadline 을 넘기면 이벤트·알림만 남긴다(작업은 계속).

Q: 멱등 키가 없으면 무슨 문제가 생기나?
A: 네트워크가 끊겨 외부 시스템이 응답을 못 받고 다시 보내면 같은 운반이 두 번 생깁니다. 같은 external_id 면 기존 작업을 돌려줍니다.

## API-402 | 작업 목록 (402)
> 현장의 작업을 필터 없이 모두 돌려주고, 게시판의 세 탭(게시판·실행 중·이력)은 화면이 상태로 나눠 그립니다.

작업이 수천 건 쌓이면 응답이 커진다. 지금은 종료 작업도 `jobs.json` 에 남는 구조라 장기 운영에서는 페이지 나누기나 보관 정책이 필요하다(후속 과제로 적어 둔다).

## API-403 | 대기 작업 우선순위 변경 (403)
> pending 작업의 우선순위만 바꿉니다(−100~100). 이미 로봇에 나간 작업은 바꾸지 않습니다.

응답 JobOut 이 길다(다음 쪽까지). 필드 뜻은 8.2절 jobs.json 표(표 8.6)와 같다.

## API-404 | 작업 상세 (404)
> traffic_waiting(대기 이유), stage(다층 단계), done/total_commands(진행률)를 포함한 작업 전체 상태입니다.

## API-405 | 종료 작업 삭제 (405)
> 끝난 작업만 지울 수 있고, 교통 예약이 남아 있으면 거절합니다.

## API-406 | 종료 작업 재시도 (406)
> 같은 명령으로 새 작업을 만들고 retry_of 로 원래 작업을 가리킵니다.

## API-407 | 작업 수동 배정 (407)
> 게시판의 [배정] 버튼입니다. 로봇을 지정하지 않으면 자동 순위의 맨 앞 로봇에 줍니다. 로봇이 받을 수 없으면 409 입니다.

## API-408 | 작업 취소 (408)

## API-409 | 프리셋 API (409~413)
> 프리셋 만들기·고치기·지우기와 게시입니다. 게시(413)가 작업 게시판의 [작업 생성] 버튼입니다.

게시할 때 명령·좌표·맵을 복사하므로 프리셋을 고쳐도 이미 만든 작업은 바뀌지 않는다.

## API-414 | 충전·대기 정책 (414~416)
> 자동 충전 기준과 대기 복귀 정책을 조회·변경하고, 충전소·주차 지점이 지금 누구에게 쓰이는지 봅니다.

정책 변경(415)은 기준 사이 순서(위험 ≤ 시작 < 완료, 작업 수락 최소 < 완료)를 검사한다. 순서가 틀리면 충전을 마친 로봇이 작업을 못 받는 모순이 생긴다.

## API-417 | 예약 실행 (417~420)
> 프리셋을 요일·시각 또는 간격(10초 이상)으로 자동 게시합니다.

## API-501 | 로봇 상태 조회 (501~502)
> 플릿 전체 또는 한 대의 RobotView 입니다. 연결 상태, 작업 가능 여부, 등록·맵 동기화, 점검, 표시 상태, 마지막 State 가 들어 있습니다.

`available_for_job` 이 배정 가능 여부의 한 줄 답이다. 안 되면 이유가 같이 온다.

## API-503 | 로봇 즉시 명령 (503~506)
> 위치 힌트, 일시정지, 재개, 오류 해제입니다. 모두 InstantAction 으로 변환돼 MQTT 로 나갑니다.

재개(505)는 FMS 가 건 정지만 풀 수 있고, 로봇에서 건 정지면 409 다.

## API-507 | 현장 정지·대피 (507~510)
> 현장 운영 상태 조회, 전체(또는 맵) 정지, 정지 해제, 대피 시작·해제입니다.

대피 mode 는 pause(제자리 정지)와 pullover(주차 지점 이동) 두 가지다.

## API-601 | 승강기 API (601~608)
> 승강기 목록·연결·수정·삭제, 칸 안 로봇 복구, 내장 시뮬레이터 장애 주입, 아직 연결 안 된 승강기 구역 조회입니다.

장애 주입(604)은 시험·시연용이다. 승강기가 멈췄을 때 예비 승강기로 바꾸는지(elevator.reroute) 확인하는 데 쓴다.

## API-701 | KPI · 알림 (701~703)
> KPI 를 시간·일 단위로 집계하고, 알림을 조회·확인합니다. 이번 개발에서 KPI 에 run_id 와 존별 집계를 더합니다.

## API-704 | webhook (704~707)
> 외부 시스템에 이벤트를 밀어 주는 설정입니다. admin 만 다루고, 보낼 때 비밀키로 HMAC 서명합니다.

받는 쪽은 `X-FMS-Signature` 헤더를 같은 비밀키로 계산해 맞춰 보면 FMS 가 보낸 것이 맞는지 확인할 수 있다. 실패하면 지수 backoff 로 재시도한다.

## API-708 | 이벤트 이력 조회 (708)
> 현장·로봇·작업·종류·심각도·기간으로 거르고, after_id 로 이어서 읽습니다. 이번 개발에서 run_id 필터와 jsonl 내려받기를 더합니다.

after_id 커서를 쓰는 이유: 시각으로 페이지를 나누면 같은 시각 이벤트가 겹치거나 빠진다. 자동 증가 id 는 순서가 확실하다.

## API-801 | 인증 API (801~804)
> 현재 키의 역할 확인, 키 목록·발급·폐기입니다. 발급 응답에서만 원문 키를 보여 주고 서버에는 해시만 남깁니다.

## API-901 | 상태 점검 (901)

## ai_adapter 함수 API | ai_adapter 함수 API

대체 규칙 상자: 모델 없음·채택 안 됨·예외·NaN·100ms 초과면 규칙 값. 같은 이유의 fallback 이벤트는 분당 1회. 시간 상한을 넘으면 1분간 규칙만 쓰는 차단기를 연다.

## 7 | 심화 질의응답 — 인터페이스
Q: VDA 5050 을 "따른다"고 했는데 정식 호환인가?
A: 아닙니다. 핵심 개념(order/state/instantAction, released 통행권, order_update_id, LWT connection, factsheet)을 따랐고 필드 이름·토픽 구조는 우리 형식입니다. 정식 VDA 5050 어댑터는 2차 로드맵입니다(표 1.4 범위 밖 상자).
Q: REST API 버전은 어떻게 관리하나?
A: 경로에 /api/v1 을 두고, 필드 추가는 기본값으로 하위 호환을 지킵니다(NFR-11). 깨지는 변경이 필요하면 /api/v2 를 따로 둡니다. MQTT 토픽도 fms/v1 으로 같은 규칙입니다.
Q: WebSocket 이 끊기면 화면 데이터가 틀리지 않나?
A: 재접속하면 로봇 스트림은 전체 목록을 다시 보내고, 이벤트 스트림은 마지막 이벤트 id 이후를 이어서 받을 수 있습니다(after_id). 끊긴 동안은 메뉴 아래 연결 표시가 빨갛게 바뀝니다.
