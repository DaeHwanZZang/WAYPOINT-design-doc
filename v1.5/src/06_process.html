6.1 시스템 아키텍쳐

운영자는 목적지를 지정한다. FMS는 작업과 통행을 조율한다. 로봇은 실행 결과를 보고한다. AI 예측은 참고만 하고 통행 허가는 FMS가 결정한다. FMS는 로봇을 시뮬레이션하지 않는다. 로봇에 대해 아는 것은 MQTT로 받은 State/Connection(fleet.py)뿐이고, 로봇별 경로계획은 로봇이 한다.

그림 6.3 FMS 프로세스의 스레드와 락 (단일 프로세스 · worker 1개 전제)

새 주기 로직은 스레드를 만들지 않고 allocator.py 1초 루프의 tick 목록에 얹는다. 작업 상태 변경(배정·취소·진행·교통 전이)은 모두 JobCoordinator.lock 안에서 하고, 락 순서는 JobCoordinator.lock → _EDIT_LOCK → LocationStore._lock으로 고정한다. EventLog.record()는 큐에 넣기만 하므로 어느 스레드·락 안에서 불러도 된다. 이번 개발의 ai_adapter 호출도 이 락 안에서 일어나므로 추론 상한(100ms)을 둔다.

그림 6.4 배포 구성 (예정안) — 학교 AWS 계정·학과 GPU 서버 사용 범위는 확인 후 확정

배포 방식은 학과 확인 후 결정한다. 어느 환경이든 FMS와 로봇은 같은 MQTT 프로토콜로 동작하므로 개발과 실험은 로컬에서 먼저 진행하고, 확정된 환경으로 옮긴다. 배포 전 필수: 브로커 1883을 외부에 열면서 익명 접속을 두면 인터넷의 누구나 로봇에 작업 취소·정지·맵 교체를 보낼 수 있다. 계정 인증(+토픽 ACL, TLS), REST API 키, SSH 키 접근을 적용한다.

그림 6.9 SD-05

설계 결정 — 재배정과 점유 해제의 순서제안서 24쪽 S5 는 "job failed → 점유 해제 후 재배정"이라고 적었다. 그러나 FMS의 불변식은 "취소·오류·통신 두절은 퇴장 증거가 아니다"이고, 통신만 끊긴 로봇이 실제로는 존 안에 서 있을 수 있다. 따라서 v1.1 은 작업은 재배정하되 존 예약은 유지한다. 재시도 작업은 그 존을 피하는 다른 통로로 가거나(경로 선택에서 "확인 필요" 존 제외), 우회로가 없으면 대기한다. 시뮬레이터에서 프로세스를 kill 한 로봇은 다시 뜨지 않으므로, 실험 러너는 kill 직후 그 로봇을 존 밖 정지 상태로 재기동하거나(위치 확인 → 해제) 운영자 조치 시간을 기록한다. 이 차이는 부록 A.2 에 기록했다. 알고리즘은 6.6.10 절(재접속한 로봇의 옛 오더 취소 포함)에 있다.
