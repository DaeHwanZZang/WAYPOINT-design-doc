10.4 보안 설계

개발 환경은 편의를 위해 브로커 익명 접속, REST 인증 꺼짐(FMS_AUTH=0)으로 돈다. 배포(학교 서버)나 시연망처럼 다른 사람이 접근할 수 있는 곳에 올리기 전에는 아래 통제를 모두 켠다. 로봇 관제 서버의 위험은 정보 유출보다 "누군가 로봇을 움직이거나 세우는 것"이라, 쓰기 경로(MQTT publish, REST 쓰기)를 먼저 막는다.

그림 10.1 보안 경계와 통제

<표 10.5> 위협과 통제 (STRIDE 분류)

분류위협 (이 시스템에서)통제상태
위장 (Spoofing)가짜 로봇이 fms/v1/AMR-001/state 를 발행해 존을 비었다고 속임 / 남의 로봇에 order 발행브로커 계정 인증 + 토픽 ACL: 로봇 계정은 fms/v1/{자기 id}/state·connection·factsheet 쓰기와 …/order·instant 읽기만, FMS 계정만 order·instant 쓰기계획
변조 (Tampering)전송 중 order 의 released 변조, 맵 번들 바꿔치기MQTT TLS(8883), HTTPS 리버스 프록시, 맵 번들은 manifest 의 sha256 으로 로봇이 검증(계획), 번들 토큰(FMS_ROBOT_TOKEN)토큰 구현
부인 (Repudiation)누가 현장 정지·작업 취소·키 발급을 했는지 모름모든 쓰기 이벤트에 actor(API 키 이름) 기록, events.db 30일 보존, 키는 사람·시스템별로 따로 발급구현
정보 노출 (Information disclosure)API 키 원문 유출, webhook 비밀키 노출, 현장 맵 유출키는 sha256 해시로만 저장·발급 시 1회 표시, auth.json·webhooks.json 파일 권한 600, 데이터 폴더 백업 암호화(계획), 맵 조회도 viewer 키 필요구현 + 계획
서비스 거부 (DoS)State 폭주(가짜 로봇 다수), REST 대량 요청으로 락 점유ACL 로 미등록 로봇 ID 발행 차단, 브로커 max_connections·메시지 크기 제한, 리버스 프록시 요청 수 제한(계획). 미등록 로봇 상태는 저장만 하고 배정·교통에 쓰지 않는다(구현)부분
권한 상승 (Elevation)viewer 키로 로봇 정지, operator 키로 키 발급라우터마다 authorize 의존성: GET=viewer, 쓰기=operator, 키·webhook·현장 삭제=admin. 마지막 admin 키 삭제 금지구현
# broker/mosquitto.prod.conf (배포용, 계획)
listener 8883
cafile /etc/mosquitto/certs/ca.crt
certfile /etc/mosquitto/certs/server.crt
keyfile /etc/mosquitto/certs/server.key
allow_anonymous false
password_file /etc/mosquitto/passwd          # mosquitto_passwd -c passwd fms ; 로봇마다 계정 추가
acl_file /etc/mosquitto/acl
max_connections 200
max_packet_size 262144                       # 256 KB (Mosquitto 2.x) (State 는 수 KB, 맵은 MQTT 로 보내지 않음)

# /etc/mosquitto/acl
user fms
topic readwrite fms/v1/#
topic readwrite elev/v1/#
topic readwrite door/v1/#
pattern write fms/v1/%u/state                 # %u = 로그인 계정 = 로봇 ID
pattern write fms/v1/%u/connection
pattern write fms/v1/%u/factsheet
pattern read  fms/v1/%u/order
pattern read  fms/v1/%u/instant
user viewer
topic read fms/v1/#

로봇 쪽(C++ comm.cpp)·뷰어·FMS 세 곳 모두 username/password·TLS 옵션을 지원해야 한다(잠재 이슈 P8). LWT 는 로봇 계정으로 접속할 때 맡기므로 ACL 의 fms/v1/%u/connection 쓰기 권한이 LWT 발행에도 쓰인다.

항목값 · 확인 방법
REST 인증FMS_AUTH=1, admin 키는 FMS_ADMIN_KEY 로 지정하거나 첫 기동 로그에서 받아 보관, 이후 사람·시스템별 키 발급

백업 · 복구

# 백업 (매일 03:00, FMS 실행 중에도 가능) — FMS_DATA_ROOT 전체
sqlite3 "$FMS_DATA_ROOT/events.db" ".backup '$BK/events.db'"     # WAL 중에도 일관된 사본
rsync -a --exclude events.db* "$FMS_DATA_ROOT/" "$BK/"            # JSON 은 원자 교체라 그대로 복사해도 한 시점 파일
tar czf "fms-$(date +%F).tgz" -C "$BK" . && 보관 14일

# 복구 — FMS 를 멈춘 상태에서
systemctl stop fms
tar xzf fms-YYYY-MM-DD.tgz -C "$FMS_DATA_ROOT"
systemctl start fms        # 재시작 복구(NFR-05)와 같은 경로로 작업·예약·임대가 올라온다
복구 후 반드시 확인할 것백업 시점 이후 로봇이 움직였으면 traffic.json 의 예약이 현재 위치와 맞지 않는다. FMS 는 새 State 의 증거로만 예약을 풀므로 위험하지는 않지만(존 밖에 있는 로봇의 예약은 정지 보고로 곧 풀림), 존 안에 있다고 기록된 로봇이 실제로 없으면 "확인 필요"로 남는다. 복구 직후 SC-12 교통 상태에서 확인 필요 존을 점검하고 로봇 위치를 확인한 뒤 해당 작업을 정리한다.
