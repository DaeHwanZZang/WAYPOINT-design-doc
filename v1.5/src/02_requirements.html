2. 요구사항 정의

2.1 서비스 구성 및 개요

본 서비스는 데이터 수집(실험 러너·시뮬레이터) → AI 학습(학과 GPU 서버 또는 로컬) → AI 서비스(FMS 서버 안의 ai_adapter) → 클라이언트(웹 관제 화면)의 네 부분으로 구성된다. 그림 2.1은 두 개의 순환을 보여준다. 위쪽 운영 루프는 운반 요청부터 로봇 상태 보고까지 실시간으로 돌고, 아래쪽 학습 루프는 운행 기록을 모아 모델을 학습·평가해 FMS에 되돌린다. 두 루프는 FMS의 ai_adapter에서 만난다. AI 결과는 배차 비용·통로 선택·충전 후보·점검 후보에 참고값으로만 들어가고, 통행 허가는 FMS 규칙이 계속 결정한다.

그림 2.1 서비스 시나리오 구성도 (운영 루프 ①~③, 학습 루프 ④~⑧)

<표 2.1> 서비스 절차와 효과

순서절차효과
①운영자가 웹 관제 화면에서 프리셋을 게시하거나 작업(이동·대기·적재·하차·도킹·주차 단계 목록)을 만든다. 외부 시스템은 같은 REST API에 멱등 키(external_id)를 붙여 주문한다.운영자는 목적지만 지정하고 누가·어느 길로는 FMS가 정한다.
②FMS가 1초마다 대기 작업을 우선순위 순으로 보고 비용이 가장 낮은 가용 로봇을 고른다. 오더에 점유 존의 대기·출구 node를 끼워 넣고, 허가한 구간까지만 released=true로 보낸다. 예약은 MQTT 발행 전에 traffic.json에 저장한다.병목에서 한 대씩만 지나가 충돌·교착이 없다. FMS가 재시작해도 예약이 복원된다.
③로봇은 허가된 노드까지 스스로 A* 경로로 가고 200ms마다 State를 보고한다. FMS는 대기 node 정지·출구 통과·차체 이탈을 확인할 때마다 통행권을 넓힌다(order_update_id 증가).시간이 아니라 위치 증거로 허가·해제해 지연·통신 끊김에도 겹치지 않는다.
④FMS는 배정·교통 대기·충전·정지 이벤트를 events.db에 쌓는다. 실험 러너는 운행 ID(run_id)·조건·seed·커밋 해시와 이상 주입 시각을 운행 폴더에 남긴다.재현 가능한 운행 데이터가 쌓인다.
⑤데이터셋 스크립트가 운행 단위로 기록을 읽어 배정 순간의 스냅샷으로 특징을 만들고, 실제 대기·잔량·주입 시각을 라벨로 붙인다. seed 단위로 학습/평가를 나눈다.미래 정보 누출과 운행 간 섞임을 막는다.
⑥규칙 기준선 → 회귀 트리 → (데이터가 충분하면) 시계열 모델 순서로 학습하고, 평가 seed에서 기준선과 비교한다."AI를 썼다"가 아니라 "규칙 대비 N% 개선"으로 보고한다.
⑦채택 기준을 넘은 모델 파일과 model_card를 FMS가 읽는다. ai_adapter가 예상 대기·작업 후 잔량·이상 점수를 계산하고, 실패하면 규칙 값을 돌려준다.AI 장애가 관제 장애로 번지지 않는다.
⑧예상 대기는 배차 비용과 통로 선택에, 예상 잔량은 충전 후보에, 이상 점수는 웹의 점검 후보에 들어간다. 3단계 운행 기록으로 다시 학습한다.우회가 생기며 바뀐 혼잡 패턴에도 예측이 맞는다.

2.3 AI학습서버의 요구사항

유스케이스 명세

핵심 유스케이스 8개의 흐름을 명세한다. 나머지는 2.5·2.6 요구기능 표와 6장 시퀀스에서 다룬다.

UC-01 작업 게시 (운영자) — 요구기능 FR-U-04 · 화면 SC-05/06 · 시퀀스 SD-01
사전 조건현장·활성 맵·목적지·프리셋이 있다. 로봇이 등록돼 배정 맵의 uid·활성 버전을 보고하고 있다.
기본 흐름1. 작업 게시판에서 프리셋·배정 방식(자동/직접)·우선순위·그룹·시작 시각·마감을 고른다. 2. [작업 생성]을 누르면 FMS가 명령·목적지 좌표·맵을 복사한 작업(pending)을 만든다. 3. 배정 루프가 1초 안에 후보 순위를 매겨 로봇에 오더를 보낸다. 4. 게시판 "배정·실행 중" 탭에 진행률이 갱신된다.
대안 흐름2a. 시작 시각이 미래면 그때까지 배정하지 않는다. 3a. 후보가 없으면 대기 이유("배터리 부족", "점검 중", "현장 정지 중" 등)를 표시하고 다음 tick에 다시 본다. 3b. 직접 배정 로봇이 바쁘면 409.
사후 조건job.assigned 이벤트, 교통 예약이 traffic.json에 저장된다.
UC-02 점유 존 통행 허가 (타이머·로봇) — FR-S-03 · SD-02
사전 조건맵에 점유 존과 방향별 대기·출구 node가 있다. 로봇 클라이언트가 traffic_control을 지원한다(Factsheet).
기본 흐름1. 층 정원을 확보한다. 2. 대기 node를 예약하고 그 node까지 허가한다(주변 차체 여유 검사). 3. 대기 node 도착·정지를 State로 확인하고, 존과 출구 공간이 비면 존을 예약해 출구까지 허가한다. 4. 출구 통과와 차체 전체의 존 이탈을 확인하면 존을 해제하고 다음 구간으로 넘어간다. 5. 오더 종료 후 IDLE 보고 시 층 허가를 반납한다.
대안 흐름3a. 같은 맵 다른 로봇 상태가 불명확하면 신규 진입을 보류한다. 3b. 대기 node 앞을 유휴 로봇이 막으면 그 로봇을 가까운 주차 지점으로 보낸다(60초에 1회). 4a. 취소·오류·통신 두절이면 예약을 유지하고 존을 "확인 필요"로 표시한다.
사후 조건traffic.wait/wait_end(+zone_id) 이벤트, 예약 파일 갱신.
UC-03 예상 대기를 반영한 통로 선택 (타이머·ai_adapter) — FR-S-02 · AI-01 · SD-09
사전 조건맵 정책 route_policy가 rule 또는 ai. 같은 목적지로 가는 gate 순서 후보가 둘 이상이다.
기본 흐름1. ZonePlanner가 후보 경로(지나갈 존 순서)를 만든다. 2. 경로마다 이동 시간(거리 ÷ 평균 속도)과 존별 예상 대기를 더한다. 3. 비용이 가장 낮은 경로의 대기·출구 node를 오더에 넣는다. 4. 후보·비용·정책을 route.choice로 기록한다.
대안 흐름2a. AI 추론 실패·100ms 초과면 예약 수 규칙 값을 쓴다. 2b. 등록된 장애물로 막힌 후보는 뺀다.
사후 조건진입 허가는 UC-02 그대로다. AI는 경로 선택에만 쓰인다.
UC-04 장애 감지·재배정 (타이머·브로커) — FR-S-08 · SD-05
사전 조건로봇이 작업 수행 중이다.
기본 흐름1. 로봇 프로세스가 죽으면 브로커가 LWT CONNECTION_BROKEN을 발행한다(또는 State 3초 미수신 → STALE). 2. FMS가 그 로봇을 배정 후보에서 뺀다. 3. 활성 작업을 failed(robot_lost)로 끝내고 같은 명령의 재시도 작업을 만든다. 4. 다음 tick에 다른 로봇에 배정한다(목표 5초 이내).
대안 흐름1a. FATAL 오류 보고면 로봇이 오더를 폐기하고 FMS가 작업을 failed 처리한다. 원인이 작업·맵(경로 없음, 통행 차단)일 수 있어 자동 재시도는 하지 않고 운영자가 [재시도]를 고른다. 3a. 장애 로봇이 점유 존 안이면 그 존은 "확인 필요"로 남아 다른 로봇은 우회 통로를 쓰거나 대기한다.
사후 조건job.failed·job.assigned(retry_of), 30초 지속 시 알림 robot_offline.
UC-05 맵 업로드·활성화 (관리자) — FR-A-02 · SC-08 · SD-11
기본 흐름1. 맵 ID와 파일(fms_map.json + 그리드 PNG 또는 grid_cfg.grid)을 올린다. 2. FMS가 검증하고 금지구역을 굽고 내용 해시로 버전을 만든다. 3. "업로드 후 활성화"면 활성 버전을 바꾸고 배정 로봇에 SET_MAP을 보낸다. 4. 로봇이 번들을 받아 맵을 바꾸고 새 버전을 보고한다.
대안 흐름2a. 검증 실패 시 422와 사유. 3a. 교통 예약·대기 작업이 있으면 활성화를 막는다(409).
UC-06 점유 존 편집 (관리자) — FR-A-05 · SC-07 · SD-12
기본 흐름1. 방향별 대기·출구 node를 목적지로 등록한다. 2. 실시간 맵의 ＋ → 구역 → 종류 "점유 존"으로 사각형을 그리고 회전한다. 3. 진입 방향을 추가해 대기·출구 쌍을 고른다. 4. 저장하면 새 맵 버전이 활성화되고 로봇에 전달된다.
대안 흐름4a. 다른 존과 겹치거나 경계를 공유하면 거절. 4b. 다른 사람이 먼저 편집해 base_version이 다르면 409.
UC-07 이상 징후 점검 (운영자) — FR-U-16 · AI-03 · SC-16 · SD-10
기본 흐름1. FMS가 1초마다 로봇별 최근 60초 창의 이상 점수를 계산한다. 2. 임계치를 연속 3번 넘으면 점검 후보에 올리고 근거(예: "허가 받음 · 위치 변화 없음 42초")를 보인다. 3. 운영자가 근거를 보고 [점검 전환]하거나 [무시]한다.
대안 흐름1a. 모델이 없으면 traffic.stall 규칙 결과만 후보로 표시한다.
UC-08 무인 반복 실험 (실험 러너) — FR-E-01 · SD-18
기본 흐름1. 러너가 YAML(맵·대수·시작 위치·주문 시각표·이상 주입·조건·seed)을 읽는다. 2. FMS 교통 정책을 조건에 맞게 바꾸고 로봇을 띄운다. 3. 운행 ID를 FMS에 알려 이벤트에 붙인다. 4. 15분 동안 시각표대로 작업과 이상을 주입한다. 5. 이벤트·State·메타를 운행 폴더에 저장하고 로봇을 종료한다.
대안 흐름4a. CPU 90% 초과가 기록되면 그 운행을 무효로 표시하고 같은 PC에서 다시 돈다.
