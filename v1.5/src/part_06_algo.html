6.6.1 작업 배정 — greedy 비용 순위

배정은 작업을 우선순위 순으로 하나씩 보면서 그 작업에 가장 싼 로봇을 고르는 greedy 방식이다. 전체 작업×로봇 최적 할당(헝가리안 알고리즘)은 쓰지 않는다. 이유는 세 가지다. ① 작업은 1초마다 몇 건씩 들어오는 스트림이라 한 순간의 전역 최적이 다음 순간에는 의미가 없다. ② 우선순위가 높은 작업이 비용 합 최소화 때문에 밀리는 일이 생기면 운영자가 이해하기 어렵다. ③ 최종 가용성은 dispatch 직전에 다시 검사해야 하므로(그 사이 로봇 상태가 바뀜) 순위는 "시도 순서"일 뿐이다. 이 결정은 v1.0 의 OR-Tools 최적 배정 비교를 범위에서 뺀 것과 같은 맥락이다(부록 A.3).

6.6.2 통로 선택 — ZonePlanner

FMS 는 로봇의 실제 주행 경로를 계획하지 않는다. 대신 "어느 점유 존을 어느 방향(gate)으로, 어떤 순서로 지날지"만 정해 오더에 대기·출구 node 를 끼워 넣는다. 이 선택을 위해 출발점·목적지·모든 gate 의 대기/출구 node 를 꼭짓점으로 하는 작은 그래프를 만들고 Dijkstra 로 최단 경로를 찾는다.

그림 6.31 ZonePlanner 그래프 — 대기→출구 간선만 그 존을 지날 수 있다

ZonePlanner(model, zones, state):
    free = (격자 == FREE) 를 로봇 반폭(ceil(width/2/res) px) 원판으로 팽창   # 로봇 planner.cpp 와 같은 규칙
    margin = radius(state) = hypot(width, length)/2 + 0.1                      # 회전해도 차체가 들어가는 외접원 + 여유

mask(allowed):                       # allowed 존만 열고 나머지 점유 존·맵 장애물은 막은 격자 (캐시)
    for z in zones, z ≠ allowed: 회전된 사각형 + margin 을 막음
    for (x, y, w, h) in obstacles: 사각형 + (width/2 + 0.05) 를 막음

distance(a, b, allowed): mask(allowed) 위 8방향 A* (대각선은 양옆이 열려 있을 때만), 결과 × res (캐시)

route(start, goal):
    if start 또는 goal 이 어떤 존 안/경계: TrafficError("존 내부에는 시작점·목적지를 둘 수 없다")
    V = [start, goal] + [g.wait, g.exit for 모든 gate]
    E: (start 또는 exit) → (goal 또는 wait)  비용 distance(·,·, None)      # 모든 존을 막고
       wait_k → exit_k                       비용 distance(·,·, zone_k)    # 그 존만 열고
           (대기·출구 node 가 다른 존과 겹치는 gate 는 간선을 만들지 않는다)
    Dijkstra(start → goal) → 지난 (zone, gate) 목록 반환, 길이 없으면 TrafficError

6.6.3 점유 존 통행 허가·해제

통행 허가는 예약(lease)과 통행권(released) 두 층으로 이뤄진다. 예약은 FMS 내부 장부(traffic.json)이고, 통행권은 로봇에 보내는 오더 노드의 released 표시다. 예약을 먼저 저장한 뒤에만 통행권을 넓힌다. 예약을 푸는 것은 로봇이 보낸 새 State 의 증거뿐이고 시간 만료(TTL)는 없다.

        events.record("job.stale_order_canceled", ...)
설계 판단 — 왜 끊긴 로봇의 작업을 다시 주는가로봇은 MQTT 가 끊겨도 멈추지 않고 이미 허가된 노드까지는 계속 달린다(시뮬레이터 코드 확인). 따라서 "프로세스 사망"과 "네트워크 단절"을 FMS 는 구분할 수 없다. 단절이면 원래 로봇과 재시도 로봇이 같은 운반을 할 수 있다. 그래도 재배정하는 이유: ① 허가 밖으로는 못 가므로 안전 문제는 없고 중복 운반이라는 업무 문제만 남는다. ② 재접속 즉시 옛 오더를 취소해 중복 구간을 짧게 만든다. ③ 시뮬레이터 실험에서 장애 주입은 kill 이라 단절 오판이 없다. 실물 로봇 단계(2차)에서는 "통신 두절 N초면 로봇이 스스로 정지"하는 로봇 쪽 규칙을 추가한다(후속 과제).

재시도 작업이 장애 로봇이 서 있는 존을 지나야 하면 그 존은 예약이 남아 있어 진입 허가가 나지 않는다. 계획: ZonePlanner 에 "확인 필요" 존을 장애물로 넘겨(set_obstacles) 우회 gate 를 먼저 고르게 한다. 우회로가 없으면 재시도 작업은 대기 node 앞에서 기다리고, 운영자가 현장 확인 후 예약을 정리한다.

6.6.11 교착 비켜 세우기 — 자동 양보 계획

pick_yield(deadlock):                                  # analyze 결과에 순환이 있고 30초 안에 안 풀릴 때
    candidates = [r ∈ 순환 로봇 |
                  r 의 작업 대기 이유 ∈ {"점유 존 진입 허가 대기", "대기 node 사용 중"}
                  ∧ r 이 정지(|v|<0.01) ∧ 모든 점유 존 밖(¬intersects)]
    if ¬candidates: 알림만 (운영자 조치)                 # 존 안 로봇은 건드리지 않는다
    y = min(candidates, key=(priority, −dispatched_at, robot_id))   # 우선순위 낮고 늦게 배정된 로봇
    cancel(y.job, reason="교착 양보")                    # 취소 확인 후
    → y 의 wait 예약은 '작업 종료 ∧ 정지' 증거로 reconcile 이 푼다 (불변식 유지)
    → BatteryManager.move_aside(y) 로 가장 가까운 빈 주차 지점
    → 원래 작업은 같은 명령으로 재게시(retry_of, priority 유지) — 순환이 풀린 뒤 다시 배정
    events.record("traffic.yield", robot=y, cycle=robots)

이 방식은 이미 내보낸 통행권을 "회수"하지 않는다. 양보 로봇의 작업을 정상 취소하고, 그 로봇이 존 밖에 서 있다는 증거로 예약이 풀리게 한다. 따라서 불변식 ②③을 지킨다. 검증은 S4 시나리오(양방향 통로 두 개가 엇갈린 맵)에서 순환 발생 → 30초 안 해소, 미해소 0회를 본다(표 1.5 #2).

6.6.12 AI 추론 차단기 계획

class Breaker:                                        # ai_adapter 안, 모델 종류별 하나
    state ∈ {CLOSED(정상), OPEN(규칙만), HALF(시험 1회)}
    call(fn, features, rule_value):
        if state == OPEN ∧ now < open_until: return rule_value, "rule"
        if state == OPEN: state = HALF
        t0 = now; try: y = fn(features) except: y = None
        ms = now − t0
        if y is None ∨ isnan(y) ∨ ms > FMS_AI_TIMEOUT_MS:
            record_fallback(reason)                  # ai.fallback, 같은 이유는 분당 1회
            if ms > TIMEOUT ∨ state == HALF: state = OPEN; open_until = now + 60초
            return rule_value, "rule"
        state = CLOSED; stats.update(ms); return y, "ai"

추론은 호출 스레드에서 동기로 한다. 100ms 는 "넘으면 그 결과를 버린다"는 사후 판정이라 그 한 번의 지연은 막지 못한다. 대신 한 번 넘으면 1분 동안 모델을 부르지 않아 지연이 반복되지 않는다. 모델이 작아(트리 300개, 1ms 수준) 실제로 열릴 일은 드물 것으로 본다(추정, 본 실험 ④ 로그로 확인).

6.7 클래스 설계

FMS 의 핵심 클래스와 의존 관계다. 락을 가진 클래스는 JobCoordinator 하나이고, 나머지 조율 클래스(Traffic·Battery·Elevator)는 그 락 안에서 불린다는 전제로 짜여 있다. 이번 개발의 RouteCostPolicy 와 ai_adapter 는 ZonePlanner·assign 에 비용만 공급하는 위치에 들어가, 허가를 만드는 TrafficController.update 와는 연결되지 않는다.
